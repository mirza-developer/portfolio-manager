# PortfolioManager

Automatic crypto portfolio manager. **Tether (USDT) is the main currency.** Every hour each position is re-valued;
a trailing stop-loss sells ALL of an asset when it falls more than the user's limit (default 5%) below its benchmark
(its highest value so far). Sale proceeds and profits stay in USDT and are reinvested, which compounds the profit.
New cryptos are added as data (an `Asset` row), never as code. No profit is guaranteed.

## Worker (Windows Service)

`TradingWorker` only runs a cycle at start and then every `Trading:CycleInterval` (default 1 hour), each in a fresh DI scope,
and logs failures without stopping. All trading logic stays in Core. Configure in `appsettings.json` (`Database`, `Trading`).

```
dotnet publish src/PortfolioManager.Worker -c Release -r win-x64 --self-contained false -o publish
sc create PortfolioManagerTrading binPath= "C:\full\path\publish\PortfolioManager.Worker.exe" start= auto
sc start PortfolioManagerTrading
```

The worker does not migrate the database: start the Web project once (it migrates and seeds), or run the migrations yourself.
It uses the simulated price provider and trade executor (`Trading:PriceProvider = Simulated`); no real money is involved.

## Core at a glance (all trade logic lives here)

- `Domain/`            Asset, Portfolio, Position, TradeLog, PriceLog (plain classes, no EF attributes)
- `Calculation/`       `StopLossEvaluator` (trailing stop), `PortfolioValuator`, `ReentryPolicy`
- `Strategy/`          `IBuyStrategy` (plug-in point for the AI), `EqualWeightBuyStrategy`, `TradeRuleGuard` (hard rules)
- `Execution/`         `SimulatedTradeExecutor` (fee + slippage, no real money)
- `Prices/`            `SimulatedPriceProvider` (deterministic random walk)
- `Engine/`            `TradingEngine.RunCycleAsync` (one cycle) and `CycleResult`
- `ServiceCollectionExtensions` `AddTradingCore()`, `AddSimulatedExchange()`

### The rules, exactly

1. Value of a position = quantity x price (USDT). Portfolio value = USDT balance + positions.
2. Benchmark starts at the purchase value (v0) and only moves up while holding.
3. Sell everything when `value < benchmark x (1 - limit/100)` (strictly less: exactly at the limit is kept).
   The per-position override beats the portfolio limit.
4. After a sale the position is in Cooldown. It can be bought again only when the cooldown is over AND the price is at
   least `ReentryRecoveryPercent` above the last sell price.
5. Reinvest: investable = USDT - cash reserve. The strategy proposes, `TradeRuleGuard` enforces max allocation per
   asset, the reserve, and the minimum trade size. A new buy starts a new benchmark, so earlier profit is in the new base.
6. An asset sold in a cycle is never rebought in the same cycle. Stop-loss always runs before buys.
7. A missing or non-positive price skips that asset, and blocks new buys for a portfolio that holds it (its value would be unreliable).
8. `IsAutoTradingEnabled = false` skips the whole portfolio (including the stop-loss).
9. A failing portfolio is rolled back (the engine works on a copy) and the other portfolios continue.

### Small differences from the written spec

- `IAssetRepository` has only `GetAllAsync` (disabled assets still need prices so held ones stay protected).
- `ITradeExecutor` is async and takes the `Asset` (a real exchange needs that).
- `RunCycleAsync` returns a `CycleResult` (processed / failed / trades) instead of nothing.
- A held position that has no price blocks new buys for that portfolio (rule 7).
- Holding positions are not topped up; USDT is invested in assets that are not held (new or re-entering).

## Data project at a glance

- `AppDbContext` (Identity + Assets, Portfolios, Positions, TradeLogs, PriceLogs); mapping in `Configurations/`.
- Decimals are `(28,10)`; every `DateTime` is stored as UTC and read back with `Kind = Utc` (both providers).
- Unique: `Asset.Symbol`, `(PortfolioId, AssetId)`. Deleting a portfolio deletes its positions; portfolios with logs cannot be deleted.
- `AddDataLayer(IConfiguration | DatabaseOptions)` selects SQL Server or SQLite (`Database:Provider`, `Database:ConnectionString`,
  `Database:AutoMigrate`), registers `IDbContextFactory<AppDbContext>` (Blazor), a scoped context, the Core repositories
  and `IUnitOfWork`, and Identity (users `ApplicationUser`, roles `Admin` / `User`).
- `EfUnitOfWork` discards the pending changes of a failed save, so one failing portfolio cannot poison the next save.
- `DbSeeder` (idempotent): roles, admin user (`Seed:AdminEmail`, `Seed:AdminPassword`), GOLD and SILVER assets,
  optional demo portfolio (`Seed:CreateDemoPortfolio`). `InitializeDatabaseAsync()` migrates (if `AutoMigrate`) and seeds.
- `Data.Tests`: migrations apply on SQLite, both providers' snapshots match the model, repository round-trips, constraints,
  cascade/restrict, unit-of-work rollback, seeder, provider registration, and the real Core engine on the real repositories.

### Notes for the Data project (P2)

- Create one `DbContext` instance per portfolio (or save through a unit of work that can discard failed changes):
  the engine calls `SaveChangesAsync` once per portfolio, and an EF context that threw on save is unusable.
- Avoid decimal `SUM`/`ORDER BY` in SQL (SQLite cannot do it) and use `DateTime` UTC, not `DateTimeOffset`.
